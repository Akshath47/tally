# Architecture

## Overview

```
iPhone Safari / PWA
  → Cloudflare Access (Worker-level policy: owner's email only)
  → one Worker "tally"
       ├─ static assets (React SPA, SPA fallback); Access-protected at the edge
       ├─ /api/* (run_worker_first) → Hono → JWT check middleware → routes
       └─ scheduled() → importer module
  → D1 "tally-prod" (Drizzle schema, migrations stored in the repo)
  → Lunch Flow Personal API (key in a Worker secret)
```

## Components

- **Frontend:** React + Vite + TypeScript + Tailwind + TanStack Query. It is built with `@cloudflare/vite-plugin` and deployed as the same Worker's static assets.
  - React escapes all text.
  - `dangerouslySetInnerHTML` is banned by a lint rule.
  - A strict CSP is set.
  - Imported descriptions are untrusted text.
- **API:** Hono on Workers, mounted at `/api`. Every route goes through the Access JWT middleware (see below).
- **Importer:** `src/worker/importer/` is a plain module called by both the `scheduled` handler and `POST /api/import`. It is not a separate service.
- **Database:** Cloudflare D1 with Drizzle. Migrations are generated by `drizzle-kit` and applied with `wrangler d1 migrations apply`.
- **Overlap lock:** a lease row in D1 that is claimed with a conditional `UPDATE`. Durable Objects would be overkill.
- **Observability:** Workers Logs (`observability.enabled`). Logs record counts, statuses and durations only, never response bodies or headers.

## Why the Worker validates the Access JWT itself

On Workers with Static Assets, the internal asset router **does not pass `ctx.access`** to the user Worker ([docs](https://developers.cloudflare.com/workers/configuration/cloudflare-access/)). So the API validates `Cf-Access-Jwt-Assertion` itself, in this order:

1. The header is present.
2. The signature is valid against `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs` (checked with `jose`; JWKS cached per isolate).
3. `aud` equals `ACCESS_AUD`.
4. `email` equals `ALLOWED_EMAIL`.

Anything else gets 401/403. `POST` requests also have their `Origin` checked. This protects the API even if the Access configuration is changed by mistake.

## Why bulk upserts use `json_each`

The D1 free tier allows 50 queries per invocation, and each statement in `batch()` counts separately. It also allows 100 bound parameters per query and 100 KB per statement. So each chunk of transactions is sent as **one JSON parameter** in one statement:

```sql
INSERT INTO transactions (...)
SELECT ... FROM json_each(?1)
ON CONFLICT(account_id, provider_txn_id) DO UPDATE SET ...
WHERE <any bank field actually changed>
```

That is one statement per ~80 KB instead of one per row. The `WHERE` clause avoids pointless row writes and gives accurate "updated" counts.

## Environments

| Env | Runtime | D1 | Lunch Flow key |
|---|---|---|---|
| Local | `wrangler dev` / Vite plugin | Local Miniflare SQLite | `tally-dev` destination key in `.dev.vars` (gitignored) |
| Production | Worker `tally` on `workers.dev` | Remote `tally-prod` | `tally-prod` destination key in `wrangler secret` |

- There is **no remote preview environment in Phase 1**. `preview_urls: false` is set because version/preview URLs share the production bindings, including the D1 database.
- Worker-level Access covers every hostname (workers.dev, custom domains, previews) ([changelog](https://developers.cloudflare.com/changelog/post/2026-08-14-workers-access/)).
- The two Lunch Flow API destinations mean the dev key can be revoked without touching production.

## Scheduling

- Cron runs hourly during Phase 1 verification, then every 6 hours. Lunch Flow's docs say data updates daily, so more frequent runs add nothing.
- Cron expressions are in UTC.
- "Today" and month boundaries are calculated in `Europe/London`.

## Freshness semantics

The Personal API has no refresh endpoint, so importing only reads Lunch Flow's cached data. It cannot trigger a bank refresh. The UI labels the button **"Import from Lunch Flow"** and shows three separate signals:

1. **Last successful import:** our own import time.
2. **Newest transaction date:** the most recent `txn_date` seen for the account.
3. **Last data change:** the last import that actually inserted or changed a transaction.

## Default decisions (change any of these on request)

- **Access login:** Cloudflare Access one-time PIN to the owner's email (`akshathyennam@gmail.com`). Google/GitHub IdP is an alternative.
- **Hostname:** `tally.<subdomain>.workers.dev`. A custom domain is optional later.
- **Access session length:** about 1 month, to avoid frequent re-login on the phone.
- **Import policy:** never delete transactions. Pending transactions that disappear are *marked*, not removed.
- **Test fixtures:** synthetic only. No real transactions in git.
